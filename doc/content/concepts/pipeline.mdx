# 同步管线

## `defineConfig` 在干什么

`cli/src/config.ts` 里的 `defineConfig()` 会把三层信息合并起来：

1. 默认值
2. 用户全局配置 `~/.aindex/.tnmsc.json`
3. 项目级 `plugin.config.ts` 传入的程序化配置

最终输出：

- `context`
- `outputPlugins`
- `userConfigOptions`

## 输入侧与输出侧是分开的

执行模型大致可以理解为：

1. 先加载用户配置并完成默认值合并。
2. 收集输入上下文，例如 workspace、rules、skills、commands、sub-agents、global/workspace prompts。
3. 把输入上下文转成输出上下文。
4. 验证输出插件能力与 `outputScopes` 覆盖是否合法。
5. 让每个输出插件声明要写哪些文件，再由核心运行时统一执行写入。

```mermaid
flowchart LR
  A["defineConfig()<br/>默认值 + 全局配置 + 项目配置"] --> B["输入收集<br/>workspace / rules / skills / prompts"]
  B --> C["上下文转换<br/>input context -> output context"]
  C --> D["输出校验<br/>plugin capability + outputScopes"]
  D --> E["插件声明产物<br/>目标文件与内容"]
  E --> F["统一运行时写入<br/>dry-run / clean / diagnostics"]
```

## 为什么这很重要

这意味着插件不是随手自己改文件，而是：

- 先声明目标
- 再转换内容
- 再由统一运行时完成 I/O

结果是 `dry-run`、`clean`、冲突诊断与保护规则都可以在统一模型下工作。

## 和 `clean` 的关系

`clean` 并不是“随便删目录”。它会基于输出插件声明出的产物集合与保护规则进行清理。你可以把它理解成同步管线的反向收口，而不是粗暴的目录擦除。
